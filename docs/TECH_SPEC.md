# Техническое задание на разработку и сопровождение портала SpaceCam

**Проект:** портал SpaceCam / R-Lock (бренды ПТК, ООО «Технолайт», layta.ru)
**Адрес:** https://andreyshalnov.github.io/SpaceCam/ · репозиторий: andreyshalnov/SpaceCam, ветка main
**Дата актуальности:** 02.11.2026

## 1. Общие требования

1.1. Сайт-каталог сетевого оборудования и IP-домофонии с публичной витриной, личным
кабинетом партнёра и панелью администратора. Хостинг — GitHub Pages, статический экспорт
Next.js, hash-маршрутизация (`#/...`), базовый путь `/SpaceCam`.
1.2. Динамические данные (цены, остатки, новости, проекты, пользователи) — Supabase
(PostgreSQL + Auth + RLS + REST/PostgREST). Клиентский ключ — publishable.
1.3. Язык интерфейса — русский. Дизайн — фирменная палитра (лаймовый акцент #a6ce39),
адаптивность desktop/mobile.

## 2. Публичная часть

2.1. Главная: продуктовые линейки (коммутаторы, узлы коммутации, домофония, замки R-Lock),
блок «Проекты» с переходом к объектам.
2.2. Каталог: 4 раздела, 149 карточек товаров с фото, характеристиками, документацией
(паспорта PDF), ценами и наличием из БД. Раздел «Замки и доводчики R-Lock» — 65 SKU из
каталога layta.ru.
2.3. Решения: калькуляторы (домофония коттеджа/квартир, PoE-видеонаблюдение, уличные узлы
SC-Box, СКУД, единая сеть), типовые решения, секция «Объекты на оборудовании SpaceCam»,
зелёный CTA «Нужен расчёт под ваш объект?» — в самом низу страницы.
2.4. Новости: публичная страница `#/news` — карточки «дата + текст», только опубликованные
(`published=true`), текст 16/18 px, выравнивание плашек по левому краю.
2.5. Меню: О бренде → Новости → Продукция (дропдаун) → Решения → Поддержка → Где купить →
Регистрация проекта; футер: Продукция / Компания (с «Новостями») / Контакты.
2.6. Поддержка: общий адрес products@layta.ru и контакты (В. Батищев — BatishchevVP@ptcab.ru,
А. Шальнов — ShalnovAI@ptcab.ru). «Где купить»: ЭТМ, Тинко, МСБ.

## 3. Личный кабинет и регистрация проектов

3.1. Вход по e-mail (Supabase Auth), восстановление пароля.
3.2. Партнёр: расширенные цены (по индивидуальному набору типов цен), наличие, форма
регистрации проекта (объект, компания, состав оборудования), реестр своих проектов.

## 4. Панель администратора (`#/admin-prices`)

4.1. Доступ — только роль `admin` (RLS-политики + `sc_is_admin()`).
4.2. «Цены»: матрица SKU × типы цен, редактирование с сохранением при выходе из ячейки,
формат отображения «123 134,4» (пробел — тысячи, запятая — десятичный), цифры по центру,
пустая ячейка удаляет цену; маркетплейсные типы скрыты.
4.3. «Наличие»: матрица SKU × 8 складов с итогами, цифры по центру, 0 = «под заказ».
4.4. «Импорт»: загрузка цен/остатков CSV-файлом с маппингом колонок.
4.5. «Продажи»: отчёт по движению и выручке за период, экспорт CSV.
4.6. «Проекты»: реестр проектов партнёров.
4.7. «Новости»: CRUD новостей (дата, текст, флаг «опубликовано»), черновики видит только
админ; права контролирует RLS (запись — только admin).
4.8. Выборка цен/остатков — с пагинацией по 1000 строк (PostgREST режет выборку молча);
пагинация обязательна при любых будущих правках загрузки.
4.9. «Сверка наличия»: период сверки остатков задаётся выпадающими датами начала и конца
(список дат — из `stock_snapshots`), фильтр склада («Все склады» или конкретный), поиск,
таблица «остаток на начало → на конец, изменение» с итогами и экспортом CSV. Там же —
загрузчик отчёта 1С «Анализ доступности товаров на складах» (.xlsx): дата берётся из шапки
отчёта («Период: на конец дня …») и правится вручную, артикулы нормализуются, запись —
апсёртом в `stock_snapshots` на день отчёта (кратно дню), текущее `stock` не меняет.

## 5. База данных

5.1. Таблицы: `prices` (PK sku+price_type_id), `price_types` (13 типов), `stock`
(PK sku+warehouse_id), `warehouses` (8 активных + служебные 21–29: Брак/Демозал/Недостача/
Транзит, `is_active=false`), `user_price_types`, `profiles` (роль admin/partner, флаг
доступности остатков), `projects` (form jsonb, владелец), `news`, `stock_snapshots`
(снимки остатков 1С на день отчёта: snapshot_date + sku + warehouse_id + qty; дата-склад-артикул —
уникальны, апсёрт).
5.2. RLS: публичное чтение опубликованных новостей; запись новостей — только admin; цены —
по разрешённым типам пользователя; наличие — по флагу; профили и проекты — свои + admin.
5.3. RPC: `sc_is_admin()`, `sc_can_see_stock()`, `sc_allowed_price_types()`, `is_admin()`.
5.4. Нормализация артикулов (кириллица→латиница, суффиксы) — единый мост каталог↔БД.

## 6. Сопровождение

6.1. Правки интерфейса вносятся патчами собранного чанка (уникальные якоря, count-проверки,
`node --check`), с синхронизацией prerendered `index.html` при изменении шапки/футера.
6.2. После деплоя — контроль md5 live-чанка и проверка в браузере с очисткой кеша
(GitHub Pages кеширует на 10 минут).
6.3. Документация структуры — `docs/PROJECT_NOTES.md`, бэкапы — `docs/backup/`.

## 7. Ограничения и открытые вопросы

7.1. Исходники сайта (src/) отсутствуют — при полной пересборке переносить пагинацию
загрузки, форматтеры цен, блок новостей, порядок меню и CTA.
7.2. Порядок двух стартовых новостей (одинаковая дата 20.10.2026) — на решении владельца.
7.3. Полный дамп данных БД выполняется service-ключом (скрипт `backup_supabase_full.py`).
